# 10 開発工程

## 1. 方針

**最も不確かで、最も価値の中心にあるものから確かめる。** このゲームの価値は「公平で厳しい受信の試練」にあり、3D の制作費が最も大きい。したがって、3D に投資する前に、文字だけで核心の遊びが成り立つかを確かめる。各段階の終わりに判定ゲートを置き、通らなければ次へ進まない。

期間は示さない。開発体制と予算が不明であり（[00](00-overview.md) Q9）、根拠のない日程を書くべきでないため。体制が決まった後に見積もる。

### 第1段階: ゲーム定義・設計（今回）

### 第2段階: 核心の検証（文字だけ、3D なし）

**前提**: 開発環境を決める（Unity と .NET を入れた PC、または CI）。API キーの用意。

| 作業 | 内容 |
|---|---|
| シナリオ生成の試作 | 種の乱択、構成役、検品役。100本以上を生成して多様性とあいまいさを測る |
| 評価の試作 | 突き合わせ、封印、評価役、規則表、2回目の評価 |
| 正解集の作成 | 人が正解を付けた回答を用意し、評価役の正確さを測る |
| 文字だけの遊びの試作 | 会話を読み、申し送りを書き、判定を受ける最小の画面 |
| 料金と遅延の実測 | 1試練あたりのトークン数と時間。Fable 5.2 の応答開始までの時間 |
| 公式 C# SDK の確認 | 構造化出力、拒否時の切替が使えるか |

| 判定ゲート | 基準（仮） |
|---|---|
| 評価の公平さ | 誤って A とする割合が目標未満（[05](05-ai-evaluation.md) §6） |
| 出題の公平さ | 検品を通ったシナリオで、人が読んであいまいと感じる項目がほぼない |
| 多様性 | 連続して遊んでも、同じ話だと感じない |
| 面白さ | 文字だけで、試した人が「もう一度」と思う。失敗に納得できる |
| 料金 | 1試練あたりの実測値が、事業上許容できる範囲にある |

**このゲートを通らない場合、3D の制作には入らない。** 設計に戻る。

### 第3段階: 音声の検証

| 作業 | 内容 |
|---|---|
| 声の選考 | 候補を聞き比べて、主と代替を決める（[06](06-voice-system.md) §4） |
| 音声認識の検証 | 試験用の音声で候補を比べる（[06](06-voice-system.md) §7） |
| 音声の検品の試作 | 読みの指定、聞き直しによる検査 |
| 発話終了の検出 | 3方式の試作と調整 |
| 音声での遊びの試作 | 第2段階の試作に音声を載せる。まだ 3D はない |

| 判定ゲート | 基準（仮） |
|---|---|
| 声 | 希望の声質に合う声が見つかり、30分聞いても疲れない |
| 読みの正確さ | 最重要の語の読み誤りが、検品後にほぼゼロ |
| 認識 | 重要な語の正解率が目安以上 |
| 遅延 | 聞き返しへの応答が目標時間内 |
| 公平さ | 音声が原因の失敗が起きない |

### 第4段階: 3D の縦切り

1つの地域（麓の里）を、製品に近い品質で最後まで作る。

| 作業 | 内容 |
|---|---|
| 画の基準 | URP での霧、光、植生、水。PC と対象スマートフォンでの見え方 |
| 移動とカメラ | 歩く、走る、話しかける、会話の演出カメラ |
| 人物 | 話し手1人を製品品質で。視線、身ぶり、口の動き |
| 試練の3つの型 | 実行型、伝達型、応答型を各1つ以上 |
| 罰の流れ | 灯火、結び灯籠、歪み、未達、追い稽古、分析、物言い |
| 画面 | 整理、申し送り、問い返し、判定、分析、聴き帳 |
| 主の試練 | 1つ |
| サーバー | 認証、シナリオの在庫、評価、記録、利用量の制御 |

| 判定ゲート | 基準（仮） |
|---|---|
| 没入感 | 3D が受信の体験を強めている（文字だけの試作より良い） |
| 画 | 目標の画が、PC で目標のフレームレートで出る |
| 制作費 | 1地域の制作にかかった手間から、残り4地域の見積もりが現実的 |
| 独自性 | 既存作品に似すぎていないかの確認を通る |

## 3. 並行して進められること

| 時期 | 内容 |
