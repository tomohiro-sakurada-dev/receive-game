# 07 Unityの技術構成

技術選定は、理由と比較を添えて示す。未検証の点はその旨を記す。

## 1. Unity のバージョン

| 候補 | 状況 | 評価 |
|---|---|---|
| **Unity 6.3 LTS（採用）** | 現行の LTS。サポートは 2027年12月まで（unity.com で確認） | 長期開発に向く安定版 |
| Unity 6.6 | 最新の更新版（第三者情報）。サポート期間が短い | 新機能が必要になった場合のみ |
| Unity 6.7 LTS | 2026年内の予定とされるが、公開日は確認できなかった | 公開後、本制作に入る前に移行を再検討する |

料金: Personal は年間収益・調達 20万ドルまで無料。超える場合は Pro（1席あたり年 $2,310）が必要（[00](00-overview.md) §3.2）。

## 2. 3Dレンダリング方式

| 候補 | 長所 | 短所 |
|---|---|---|
| **URP（採用）** | PC からスマートフォンまで1つの構成で動く。品質段階を機種ごとに切り替えられる | 体積のある霧や雲などの高度な表現が標準機能にない。自作か外部アセットが必要 |
| HDRP | 高品質な光、体積霧、空の表現が標準で使える | スマートフォンでは使えない（従来仕様。着手時に再確認）。PC 専用になる |
| 両方を使い分ける | — | 材質やシェーダーを二重に作ることになり、小規模体制では維持できない |

スマートフォン対応が要件にあるため URP を採る。霧はこのゲームの主題なので、URP 上での霧の表現（高さのある霧、層状の霧、光の筋）を縦切りの試作で最初に検証する。

### 品質段階

| 段階 | 対象 | 内容 |
|---|---|---|
| 高 | PC（独立した GPU） | 動的な影、霧の光の筋、水面の反射、植生の密度を最大に |
| 中 | PC（内蔵 GPU）、高性能スマートフォン | 影の距離を短く、霧を簡略化 |
| 低 | 一般的なスマートフォン | 焼き込みの光を中心に、植生を減らす |

**正直な見通し**: スマートフォンで PC の「高」と同じ画は出せない。美しさは、構図・色・霧・音の設計で保つ。会話の場面は登場人物が1〜3人で動きも少ないため、描画の予算を人物と背景に集中できる。

## 3. 性能の目標（仮。試作で確定）

| 項目 | PC | スマートフォン |
|---|---|---|
| フレームレート | 60 | 30 |
| 解像度 | 1080p 以上 | 機種に応じて可変 |
| 読み込み | 地域の切替 10秒以内 | 20秒以内 |
| アプリの大きさ | — | 初回 1GB 以下を目安。地域ごとに追加で取得 |
| 発熱・電池 | — | 30分の連続プレイで処理落ちしない |

## 4. クライアントの構成

### 層の分離

| 層 | 内容 | Unity への依存 |
|---|---|---|
| 中核（ドメイン） | 試練の進行、灯火、判定の規則表、評価基準票の扱い、弱点の記録、シナリオの種の乱択 | **なし**（純粋な C#） |
| 接続 | 中継サーバー、音声認識、音声合成との通信。障害時の代替 | 小 |
| 表現 | 3D、人物の動き、カメラ、画面表示、音 | あり |

中核を Unity に依存させない理由は2つある。Unity Editor のない環境でも自動テストができること（Claude Code が検証しながら開発できる）。そして、判定の規則表をサーバーと共通の部品として使えること。

### 主な部品

| 用途 | 採用 | 理由・比較 |
|---|---|---|
| 入力 | Input System | キーボード、ゲームパッド、タッチを同じ仕組みで扱える |
| カメラ | Cinemachine | 探索の三人称視点と、会話の演出カメラを切り替えやすい |
| キャラクター操作 | CharacterController を使った自作の移動 | 必要な動きは歩く・走る・話しかけるだけ。物理挙動による移動は制御が難しく不要 |
| 人物の動き | Humanoid のアニメーション、視線と手の補正 | 会話中の視線と身ぶりが没入感を左右する |
| 口の動き | 音声から口の形を作る部品（候補は試作で比較） | 音声合成サービスによっては口の形の情報を返すものもある |
| 画面表示 | uGUI と TextMeshPro | 縦書き、和文フォント、3D空間内への表示の実績が多い。UI Toolkit は、実行時の表現力を確認してから再検討 |
| 資産の読み込み | Addressables | 地域ごとの取得、スマートフォンの容量対策 |
| 音 | Unity 標準の音声機能とミキサー | まず標準で作る。環境音の表現が足りなければ外部の音響ミドルウェアを検討 |
| マイク | Unity 標準の Microphone | PC・iOS・Android で使える |
| 非同期処理 | Unity 6 標準の Awaitable（不足なら UniTask） | 依存を増やさない |
| データ形式 | Newtonsoft JSON（Unity 公式パッケージ） | IL2CPP での動作実績 |
| テスト | Unity Test Framework、中核は通常の .NET のテスト | §9 |

### 状態の流れ

探索 → 遭遇 → 会話 → 運ぶ → 整理 → 申し送り → 問い返し → 判定 → 分析 → 探索、を一つの状態機械として中核に置く。表現の層は状態の変化を受けて画面と音を切り替えるだけにする。通信や音声の障害はどの状態でも起こりうるので、各状態に「中断して無効試合にする」経路を持たせる。

## 5. サーバーの構成

### なぜサーバーが必要か

API キーをアプリに埋め込むと、取り出されて悪用される。また評価基準票や正解を端末に置くと、読み取られる。そのため Claude・音声サービスの呼び出しと、判定の正本を、自前の**中継サーバー**に置く。

| 構成 | 内容 | 評価 |
|---|---|---|
| アプリから直接呼ぶ | 鍵をアプリに持たせる | 販売する製品では不可。本人だけが使う試作に限り、端末の安全な保管領域に本人の鍵を置く形は許容できる |
| **中継サーバー（採用）** | アプリはゲームの操作だけを送る。指示文の組み立て、AI の呼び出し、判定はサーバーで行う | 鍵と正解を守れる。利用量を制限できる |

### サーバーの言語

| 候補 | 長所 | 短所 |
|---|---|---|
| **C#（ASP.NET Core）（推奨）** | Unity と同じ言語。中核の部品とデータの定義を共有できる。公式の C# SDK がある | SDK の新機能への対応が他言語より遅い場合がある |
| TypeScript | 公式 SDK が最も充実。実行環境の選択肢が多い | 言語が2つになり、定義を二重に持つ |
| Python | 公式 SDK が充実 | 同上 |

C# を推奨するが、構造化出力や拒否時の代替モデル切替などが C# SDK で使えるかを試作で確かめ、不足があれば TypeScript に切り替える。

### サーバーの役割

| 機能 | 内容 |
|---|---|
| 認証 | 匿名の端末アカウントから始め、任意で引き継ぎ用の連携 |
| シナリオの管理 | 生成、検品、在庫、割り当て、使用済みの記録 |
| 会話の中継 | 聞き返しを会話役に渡し、応答を返す |
| 音声の中継 | 音声合成の実行と保管。音声認識用の短時間有効な鍵の発行（対応するサービスの場合） |
| 評価 | 突き合わせ、封印、評価、規則表の適用、物言い |
| 記録 | 試練の記録、弱点の記録、判定の監査記録 |
| 利用量の制御 | 利用者ごとの回数と金額の上限、異常の検知 |

## 6. 対応機種

| 機種 | 方針 |
|---|---|
| Windows、macOS | 先行して対応 |
| iOS、Android | 後続。同じ URP の構成で品質段階を下げる |
| WebGL | **対象外**。マイク入力と端末内音声認識の対応が確認できていない |
| 家庭用ゲーム機 | 今回の範囲外 |

機種間の違いは、入力（キーボード／タッチ）、マイクの許可、音声の経路（反響除去）、品質段階の4点に集約し、中核には持ち込まない。

**通信が必須である。** 会話生成と評価はクラウドの AI を使うため、通信のない状態では遊べない。

## 7. API 利用料金の概算

**前提（すべて仮定。試作で実測して置き換える）**

- 日本語1文字を 1.5 トークンと仮定。
- 1試練あたり: 台本 800文字、聞き返し平均 1.5回、申し送り 300文字。
- 構成役: 入力 4,000、出力 6,500 トークン（思考分を含む）。
- 評価役（1回）: 入力 6,000、出力 3,500 トークン（思考分を含む）。
- A の候補が出る割合を 30% と仮定。
- 単価は [00](00-overview.md) §3.1 のとおり。

### 1試練あたりの AI 料金

| 構成 | 内容 | 概算 |
|---|---|---|
| 甲: すべて Fable 5.2、都度生成、評価は常に2回 | 仕様の文言に最も忠実 | **約 $0.8** |
| 乙: 在庫方式（20人で共有、バッチ生成）、会話役と突き合わせは Sonnet 5.5、評価は Fable 5.2 で1回＋A の候補のみ2回目 | 推奨案 | **約 $0.28** |
| 乙′: 乙と同じだが利用者が1人（共有なし） | 個人利用の場合 | **約 $0.42** |
| 丙: 乙に加え、1回目の評価を Sonnet 5.5、A の候補のみ Fable 5.2 で確認 | 最安。評価の正確さの検定が条件 | **約 $0.14** |

内訳の目安（Fable 5.2 の場合）: 構成 $0.29、検品 $0.01 未満、突き合わせ $0.02〜0.09、聞き返し応答 $0.01〜0.03、評価1回 $0.19。**料金の大半は出力トークン（思考分を含む）である。**

### 1試練あたりの音声料金

| 項目 | 概算（第三者情報の単価による） |
|---|---|
| 音声合成（800文字） | 標準的なサービスで $0.01〜0.02、高価格のサービスで $0.08 前後。在庫方式なら共有で割れる |
| 音声認識（2分） | $0.01〜0.02 |

### 1人・1か月の目安

1日6試練、月180試練と仮定した場合の AI 料金。

| 構成 | 月額の概算 |
|---|---|
| 甲 | 約 $140 |
| 乙 | 約 $50 |
| 乙′ | 約 $76 |
| 丙 | 約 $25 |

**結論**: すべてを Fable 5.2 で都度実行する構成は、個人が自分で負担する場合を除き、一般的なゲームの価格では成り立たない。販売するなら、在庫方式、モデルの使い分け、利用回数の上限、月額課金のいずれかが必要になる。これは技術だけで解決できない事業上の判断であり、[00](00-overview.md) の Q1・Q2 の回答に依存する。

料金を下げる手段: 指示文のキャッシュ（読み出しは入力単価の約40分の1）、バッチ処理（半額）、`effort` の調整（思考分の出力を減らす）、在庫の共有、モデルの使い分け。

## 8. セキュリティ

| 対象 | 対策 |
|---|---|
| API キー | サーバーだけが持つ。アプリにも、リポジトリにも置かない |
| 評価基準票・正解 | 判定が出るまで端末に送らない |
| アプリからの要求 | ゲームの操作と利用者の発言だけを受け付ける。指示文はサーバーが組み立て、アプリからは指定できない |
| AI の不正利用（無料の対話窓口として使われる） | 発言の長さ、聞き返しの回数、1日の試練数、利用者ごとの金額に上限。話し手は役から出ない |
| 指示の混入 | 利用者の文はデータとして区切って渡す。出力形式を固定し、プログラムで検査する（[05](05-ai-evaluation.md) §8） |
| 通信 | すべて暗号化する |
| 個人情報 | 収集を最小にする。音声は既定で保存しない。回答文は AI 提供者側で30日保持される旨を告知する |
| 保存データ | 進行の正本はサーバー。端末の保存は表示用の写し |
| 依存部品 | 版を固定し、既知の欠陥を定期的に確認する |
| 秘密情報の管理 | 実行環境の秘密管理機能を使う。記録に鍵や個人情報を出さない |

## 9. Claude Code による開発の進め方

| 項目 | 方針 |
|---|---|
| 中核とサーバー | 通常の .NET のプロジェクトとして作り、Unity なしで自動テストを回す。クラウド上の Claude Code でも検証できる（.NET SDK の導入が必要） |
| Unity 側のコード | Unity を入れた手元の PC で Claude Code を動かすか、Unity ライセンス付きの CI で、コンパイルとテストを確かめる |
| シーン・プレハブ・材質 | 人が Unity Editor で作る。Claude Code はスクリプト、編集用の補助ツール、テストを書く |
| 3Dモデル・動き・音楽・効果音 | **Claude Code では作れない。** 制作者に依頼するか、購入した素材を使う |
| AI の指示文 | リポジトリで版管理し、変更のたびに正解集で検定する |

**この作業環境（クラウドのコンテナ）には Unity も .NET SDK もない。** 現状のままでは Unity のコードを一度もコンパイルできない。第2段階に入る前に開発環境を決める必要がある（[10](10-roadmap.md) 第2段階の前提）。
