# 第2段階（試作版）での判断記録

- 日付: 2026-11-15
- 対象: 設計書（`docs/design/`）に矛盾・未定義があった点、および試作のために設計から変えた点
- 位置づけ: すべて**暫定**。遊んで確かめた後に見直す前提で、作業を止めないために決めた

各項目は「決めたこと」「理由」「弱点・未解決」の順に書く。

## A. 公平性と罰（最も慎重に扱った点）

### A1. 評価に AI を使わない。即失敗の根拠は、語彙の照合だけにする

- **決めたこと**: 判定はすべて、語彙の識別子の一致・不一致で機械的に決める。AI の評価役はこの試作に入れていない。将来つなぐ場合に備え、AI 由来の指摘は最大でも「中（B）」に抑え「参考」の印を付ける歯止めだけを規則表に入れた（`Rules.CapBySource`）。
- **理由**: 指示「AI評価の精度が検証できていない段階では、AIの判断だけで即失敗にしない」。監査の指摘1も同じ結論だった。
- **弱点**: 自由な言葉での回答は評価できない。A2 の入力方式とひとまとまりの判断である。

### A2. 回答は、この世界の語彙の中から選ぶ

- **決めたこと**: 申し送りの中身は、欄ごとの語彙一覧（人物14、品・事柄16、日8 など）から選ぶ。一覧は**どの会話でも同じ**で、会話の内容によって変わらない。
- **理由**: 自由記述を AI なしで公平に採点する方法がない。表記の揺れや打ち間違いを誤答と判定する事故も起きない。一覧が固定なので、選択肢が出題の手がかりになる度合いは小さい。日本語入力（IME）が Unity で確実に動くか未検証であり、入力不能で遊べなくなる危険も避けた。
- **設計との差**: 設計は「選択肢を出さず、自分の言葉で伝える」としていた（`02` §4、`01` §3）。
- **弱点**: 一覧に正解が載っているので、思い出す負荷は自由記述より軽い。測っているのは「再生」より「再認に近いもの」である。訓練効果の解釈ではこの点を割り引く必要がある。

### A3. 確度の印を4つにした

- **決めたこと**: 聞いた／推し量り／**分からない**／**言われていない**。設計の「不明」を2つに分けた。
- **理由**: 指示「不明だと正直に申告した場合は、聞き漏らしと区別する」。同じ欠落でも、「言われたが受け取れなかった」と自覚している場合と、「言われていない」と思い込んでいる場合を、回答の時点で分けて記録できる。
- **規則**（要承認事項 Q3 への暫定回答）:

| 話し手 | プレイヤーの印 | 判定 | 罰 |
|---|---|---|---|
| 言った | 分からない | 不明の申告 | なし。最重要の欄なら結果は未達 |
| 言った | 言われていない | 聞き漏らし | 最重要なら致命、重要なら中 |
| 言っていない | 言われていない | 正しい見極め | なし |
| 言っていない | 分からない | 漏らしたと思い込んだ | なし（技能の記録には残る） |

### A4. 言われていないことを「聞いた」として渡すと、欄を問わず致命的

- **決めたこと**: 要承認事項 Q4 への暫定回答。8つの欄はすべて、日時・人物・対象・数・場所・条件・行動のいずれかなので、設計の仮置きに従うと全欄が致命的になる。
- **弱点**: 「刻」や「数」の捏造まで即失敗にするのは厳しすぎる可能性がある。遊んで確かめる。「推し量り」の印を付けていれば軽微（C）にとどまる。

### A5. 受け手の問い返しを「言い換えへの応答」にした（監査の指摘5への対処）

- **決めたこと**: 受け手は欄を尋ねるのではなく、「場所は『蔵の前』——そういうことだな」と言い換えて確かめてくる。答えは「その通りです」「いいえ、違います」「そこまでは聞いていません」の3つ。言い換えには、正しいもの、値をずらしたもの、推測を断定に変えたもの、言われていない中身を足したものが混ざる。3問とも出題前に固定する。
- **理由**: 設計の問い返しは「申し送りで落としても、問い返しで訊かれて答えれば済む」抜け道があり、規則が未定義だった（指摘5）。言い換え方式では、問い返しは思い出しの助けにならない。受け手の早合点に流されないことは、「歪めずに伝える」を受け取りと分けて測る手段にもなる。
- **二重に数えない規則**: 歪曲とするのは、**自分の申し送りと食い違う答え**をしたときだけ。申し送りの時点で既に誤っていた内容に同意しても、受け取りの誤りとして1回だけ数える。
- **弱点**: 3択であり、当て推量で通る余地がある。

### A6. 食い違いの罠は入れていない（監査の指摘6）

- **決めたこと**: 話の中に訂正のない食い違いを置く罠は、この試作では出題しない。
- **理由**: 「あいまいな出題で罰しない」と正面から衝突し、解決策が定まっていない。

### A7. 未達は進行せず、同じ地で別の話をやり直す（監査の指摘7）

- **決めたこと**: 未達では灯火は減らず、試練の番号も進まない。
- **未解決**: 同じ難しさ・同じ罠の型の話に固定することは未実装。難しい話を未達で流して易しい話を待つ抜け道は、まだ残っている。

### A8. 整理は会話の直後に行う（監査の指摘8）

- **決めたこと**: 「運ぶ」過程は入れていない。会話が終わるとすぐ整理に入る。
- **理由**: 受け取りの失敗と、覚えていられなかった失敗を混ぜないため。

### A9. 追い稽古は省いた

- **決めたこと**: 中程度のミス1件につき灯火が1つ減る。追加課題で取り戻す仕組みはない。
- **理由**: 監査の指摘15（仕組みが多すぎる）。規則を減らした。

### A10. 封印と無効

- **決めたこと**: 評価データは生成時に SHA-256 の要約値を記録する。判定の直前に計算し直し、一致しなければ試練を無効にして罰を出さない。
- **理由**: 「重要情報を後付けで決めない」を、規則ではなく仕組みで守る。

## B. 文字だけで「聞く」を成り立たせる

### B1. 言葉は一度きりで消える

- **決めたこと**: 話し手の言葉は一文字ずつ現れ、語り終えると数秒で消える。記録は画面に残らない。読み返すには聞き返す（間合いを使う）しかない。
- **理由**: 文字は読み返せるので、そのままでは「聞く」訓練にならない。世界観（霧が文字を溶かす）とも合う。
- **弱点**: 消えるまでの時間は読む速さに合わせて調整が要る。語りの速さは3段階で選べるようにした。

### B2. 話が終わったかどうかは、プレイヤーが確かめる

- **決めたこと**: 「続きを聴く」「聞き返す」「承りました」の3つのボタンは、話の最初から最後まで同じ見た目で出る。話が終わっていれば、「続きを聴く」で話し手が「話はそれだけじゃ」と告げる。結びの言葉の後に追い声があるかどうかは、聴き続けなければ分からない。
- **理由**: 「最後まで聞く」を、画面の合図ではなく行動で測るため。

### B3. 聞き返しの良し悪しの分け方

| 分類 | 条件 | 技能の記録 |
|---|---|---|
| 役に立つ | あいまいな言葉の中身を訊いた／推測・伝聞・言い直しを念押しした／話が一区切りした後に、決まっていないことを確かめた | 成功 |
| 先走り | これから語られることを、語られる前に訊いた | 失敗 |
| 念押し | はっきり言われたことをもう一度訊いた | 数えない |
| 確かめずじまい | あいまいな言葉（「いつもの所」）を訊かなかった | 失敗 |

間合いは段によって 4〜2 回。数は見せず、残り1回になると相手の様子の一文で伝える。

## C. 訓練効果の測定

### C1. 七つの技能を、機会と成功の数で別々に記録する

総合点は作っていない。定義は次のとおり（実装は `Evaluator.TallySkills`）。

| 技能 | 機会 | 成功 |
|---|---|---|
| 最後まで聞く | 試練ごとに1（切り上げなかったか）。加えて、終わり際の条件・追い声・言い直しで確定する欄 | 切り上げていない／その欄の中身が合っている |
| 正確に受け取る | 上記以外の、話し手が中身を言った欄 | 中身が合っている |
| 補わない | 言われていない欄、確かめていないあいまいな欄。問い返しで中身を足された場合 | 中身を書いていない／同意していない |
| 事実と推測を分ける | 中身が合っている欄の、印の付け方。推測を断定に言い換えられた問い返し | 確かな話に「聞いた」、推測・伝聞に「推し量り」／同意していない |
| 分からないと知る | 言われていない欄。中身を受け取れなかった欄 | 「言われていない」と見極めた／「分からない」と申告した |
| 時を得て問う | 聞き返し。確かめるべきだったあいまいな言葉 | B3 の表 |
| 歪めずに伝える | 問い返しの1問ごと | 自分の申し送りと食い違う答えをしていない |

- **弱点**: 技能どうしは完全には独立していない（「補わない」と「分からないと知る」は、言われていない欄で重なる）。
- **未実装**: ゲーム外の課題による効果の確認（設計 `11` §8）。この試作で分かるのはゲーム内の成績の推移だけであり、**日常の聞く力が伸びることは示せない**。弱点に合わせた出題の重み付けも未実装。

## D. シナリオ生成

### D1. 端末内の組み立て式。AI も通信も使わない

- **決めたこと**: 人格4、用向き5、人物14、品・事柄16、日8、刻7、場所12、条件8×8、罠の型7を乱択で組み合わせ、語尾を人格ごとに変えて文を作る。
- **理由**: 指示「AIが利用できない場合も遊べる」「外部APIへの依存は最小限」。要承認事項 Q2（生成の方式）は未決のままでも進められる。
- **弱点**: 文の型が有限なので、数十回遊ぶと言い回しに既視感が出る。内容の組み合わせは重複しないが、「毎回新鮮な会話」の水準には届かない。AI による生成に置き換える余地を残してある（出題内容 `ScenarioScript` と評価データ `AnswerKey` を分けてあり、検品もそのまま使える）。

### D2. 重要度の決め方

相手・用向き・品・日・ただし書きは最重要。刻・場所・数は重要。あいまいな言葉で語られた欄だけは最重要に上げる（確かめなければ務めを果たせないため）。すべて生成時に決まり、封印に含まれる。

### D3. 段と地域

段1〜5を設計の5地域に対応させた。道行きは3試練、灯火は3つ。道行きを終えると次の段が開く。主の試練は未実装。

## E. Unity と開発環境

### E1. ブランチ

指示は「作業用ブランチを作成する」。この作業環境では、プッシュ先が `claude/happy-wright-il3l1n` に指定されており、これは `main` とは別の作業用ブランチである。新しいブランチは作らず、これを使った。

### E2. 画面は UI Toolkit、すべてコードで組む

- **決めたこと**: シーン・プレハブ・画面定義ファイルを手で書かない。`Bootstrap` がどのシーンでも起動し、画面をコードで組み立てる。背景（空・山・霧・灯火）は起動時に計算で描く。起動用シーンと URP の設定は、エディタ用スクリプトが初回に作る。
- **理由**: この環境に Unity Editor がなく、手書きのシーンや設定ファイルは壊れていても気づけない。コードなら、Unity の参照アセンブリでコンパイル検査ができる。UI Toolkit は uGUI と違いエンジン本体に含まれるので、検査の範囲に収まる。
- **設計との差**: 設計 `07` は uGUI と TextMeshPro を採るとしていた。

### E3. 和文フォントを同梱した

しっぽり明朝（Medium、SIL Open Font License 1.1）を `Assets/Receive/Resources/Fonts/` に置いた。ライセンス文を同じ場所に置いてある。約 8.7MB。OS のフォントに頼ると、表示されるかどうかが環境次第になるため。

### E4. URP

パッケージは `Packages/manifest.json` に入れた。URP の設定ファイルの作成は、URP の型を名前で探して呼ぶ方式にした。URP の版によって処理が見つからない場合は警告と手作業の手順を出し、ゲーム自体は動く。**Unity 上での動作は未検証。**

### E5. `.gitignore` に追記した

Unity 標準の `.gitignore` は `*.csproj` を無視する。Unity の外で中核を検査するプロジェクト（`dotnet/`）を管理するため、末尾に例外を4行足した。既存の行は変えていない。

### E6. Unity の `.meta` ファイルは含めていない

`.meta` は Unity が初回に生成する。生成されたらコミットすること（README に記載）。
